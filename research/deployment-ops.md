# Flotilla research — deployment / ops / security

## 1. What the comparables do

### Docker Desktop

- **Install and privilege boundary** — the normal Mac path is a downloaded DMG dragged to `/Applications`; Docker also provides a PKG for fleet/MDM deployment. First launch offers recommended or advanced setup. The app itself runs as the logged-in user and asks for authorization only for specific host changes: system-wide CLI symlinks, `/var/run/docker.sock`, low-numbered ports, and a narrowly scoped privileged helper. Advanced setup can instead put CLI links in the user's directory and avoid most privileged configuration. The command-line installer supports preconfiguration such as `--user`, proxy values, allowed organization, and admin settings. This is a useful separation between app installation and optional privileged integration. [Docker Mac install](https://docs.docker.com/desktop/setup/install/mac-install/) · [permission model](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/)
- **Uninstall and data ownership** — Troubleshoot > Uninstall and an app-bundled uninstaller are offered. Docker explicitly warns that uninstall destroys local containers, images, and volumes, documents backup first, and lists residual paths that may need manual cleanup. macOS privacy controls can prevent even the uninstaller from deleting container metadata, so "app removed" and "all data removed" are not always the same result. [Docker uninstall](https://docs.docker.com/desktop/uninstall/) · [backup and restore](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/)
- **Updates** — Settings > Software updates separates "Automatically check for updates" (on), "Always download updates" (off), and independent background updates for components such as Compose/CLI (on). Updates are notified in the menu and dashboard, may be rolled out gradually, and can also be checked/applied with `docker desktop update`; enterprise admins can disable and lock update checks so only vetted MDM versions are installed. Recent installers include automatic reversion when an installation fails, but Docker's recovery documentation still relies heavily on backup plus installing another version. [Docker settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/) · [release FAQ](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/releases/) · [update CLI](https://docs.docker.com/reference/cli/docker/desktop/update/)
- **Signing, notarization, and isolation** — Docker's public docs focus on runtime boundaries rather than listing its app entitlements. Its main Mac backend is unprivileged; root inside a container is root inside the Linux VM, not root on macOS. A root helper is used only for a small documented operation set over a protected Unix socket. Business customers can enable Enhanced Container Isolation to further isolate container root from the VM daemon. The product is distributed outside the Mac App Store, so the appropriate Mac baseline is Developer ID signing, hardened runtime, and notarization rather than assuming App Sandbox. [Docker permission model](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/) · [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
- **MDM and managed preferences** — Docker has two management layers. Sign-in enforcement can be delivered in a macOS configuration profile, which Docker calls the highest-security method because the profile is SIP-protected. Broader locked settings use `/Library/Application Support/com.docker.docker/admin-settings.json`, commonly placed with Jamf/another MDM, and require Docker Business sign-in. Settings have explicit values and lock state; update checking, analytics, extensions, proxies, registry policy, and isolation can be controlled. The fleet PKG and CLI installer flags make zero-touch deployment practical, but the management feature is tied to commercial licensing. [sign-in enforcement](https://docs.docker.com/enterprise/security/enforce-sign-in/methods/) · [managed JSON](https://docs.docker.com/enterprise/security/hardened-desktop/settings-management/configure-json-file/) · [settings reference](https://docs.docker.com/enterprise/security/hardened-desktop/settings-management/settings-reference/)
- **Licensing and activation** — users must accept the subscription agreement; personal, education, non-commercial open-source, and qualifying small-business use is free, while larger commercial/government use requires a subscription. Enterprise installation can force membership in an allowed Docker organization. This adds considerable account and entitlement machinery that has no value for a personal utility. [Docker Mac install](https://docs.docker.com/desktop/setup/install/mac-install/)
- **Telemetry and privacy** — Settings > General exposes "Send usage statistics", on by default, covering diagnostics, crashes, and usage. Enterprise policy can lock `analyticsEnabled`, although Docker notes that turning it off does not stop server-side events inherent to online services. Uploaded diagnostic bundles can include usernames and IP addresses; Docker says access is restricted and bundles are normally deleted after 30 days. [Docker settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/) · [diagnostic privacy](https://docs.docker.com/support/)
- **Logging and support bundles** — the Troubleshoot surface groups Restart, Clean/Purge Data, Reset to factory defaults, Uninstall, and Get support. Gathering produces a ZIP that can be inspected locally or explicitly uploaded to receive a diagnostic ID. The same gather flow works when the UI cannot launch. Docker documents Unified Logging/Console queries and the local component log directory. This is operationally mature, but destructive recovery actions sit close together and bundles may contain personal data. [Docker troubleshooting](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/)

### OrbStack

- **Install, migration, and privilege boundary** — OrbStack is a native Swift Mac app. Opening it is enough to set up its user-space environment; admin access is optional and is requested only to install global command links and improve compatibility via `/var/run/docker.sock`. Without approval, commands remain available under `~/.orbstack/bin`. When replacing Docker Desktop it offers an optional copy-based migration and documents side-by-side Docker contexts and an explicit route back. [OrbStack install/migration](https://docs.orbstack.dev/install) · [OrbStack FAQ](https://docs.orbstack.dev/faq)
- **Uninstall and recovery** — deleting the app removes the program; deleting `~/.orbstack` and its Group Container removes data. Its documentation also reminds users to restore the prior Docker context. This is simple, but data cleanup is manual and a user can easily leave a context pointing at a removed engine. [OrbStack uninstall](https://docs.orbstack.dev/install#uninstalling)
- **Updates and older versions** — the app contacts a separate optional update endpoint; architecture-specific distributions keep download/update size lower than a universal binary. OrbStack's product argument favors continuous updates instead of permanent old-version entitlements. Public documentation exposes "What's new" and older versions, but does not document a robust in-app rollback workflow; treat any claim about automatic rollback as **(verify)**. [OrbStack privacy](https://docs.orbstack.dev/legal/privacy) · [OrbStack FAQ](https://docs.orbstack.dev/faq)
- **Sandbox and isolation** — the app stores runtime data in an App Group container, but the documented ability to install command links, provide broad file integration, create a Docker socket, and run VMs should not be confused with Apple's App Sandbox. The useful pattern is user-space operation with optional, visible privilege escalation—not a broad always-root service. OrbStack also defaults network exposure of its Linux-machine SSH server to off. [OrbStack settings](https://docs.orbstack.dev/settings) · [architecture](https://docs.orbstack.dev/architecture)
- **Licensing and activation** — personal use is free; freelance/business/commercial use is licensed per user for up to five devices. A 30-day Pro trial degrades to free personal mode, and activation is app sign-in. Organizations add pooled seats, domain joining, and SSO; the privacy policy says the license API is required and an on-premise license server is negotiable. This is a clean commercial grace-period model, but unnecessary for Flotilla. [OrbStack licensing](https://docs.orbstack.dev/licensing)
- **Crash reporting, telemetry, and diagnostics** — the privacy policy distinguishes required license traffic from optional update checks, explicit diagnostic uploads, and optional anonymous Sentry crash/error reports. A submitted report may contain app logs, machine names/list, settings, and other relevant system information. The separation of endpoints is transparent; the automatically collected "usage data" language is broader than the product UI documentation, so exact opt-out controls are **(verify)**. [OrbStack privacy](https://docs.orbstack.dev/legal/privacy)
- **Managed deployment** — unlike Docker, Podman Desktop, Rancher Desktop, and Tailscale, OrbStack's public documentation does not expose a substantial Jamf/configuration-profile schema **(verify)**. It is therefore a weaker model for Flotilla's managed-host phase even though it is the closest native Mac UX analogue.

### Podman Desktop

- **Install and dependency onboarding** — Podman Desktop recommends a universal DMG rather than Homebrew because mixing installer sources can produce path conflicts. The drag-to-Applications app then runs an onboarding wizard that installs the Podman engine with a macOS authorization prompt, creates the VM, and optionally installs companion CLIs. Setup can be skipped and resumed from Dashboard or Settings > Resources. This is very close to Flotilla's separate-app/separate-runtime dependency problem. [Podman Desktop Mac install](https://podman-desktop.io/docs/installation/macos-install)
- **Uninstall is layered** — removing the GUI does not remove Podman machines, containers, clusters, engine binaries, configuration, or extension storage. The official sequence names each layer and its destructive command/path. The thoroughness is good; requiring a long manual recipe is not. [Podman Desktop uninstall](https://podman-desktop.io/docs/uninstall)
- **Updates** — Podman Desktop can update the Podman engine it manages; extension update checking and automatic installation are separate preferences. The Mac app uses differential-download support and reminder preferences, but current user docs do not clearly specify the full application-update trust/rollback path **(verify)**. Its open-source Electron implementation is an alternative to Sparkle, not a reason to overturn Flotilla's settled native/Sparkle choice. [Podman Desktop repository](https://github.com/podman-desktop/podman-desktop) · [settings reference](https://podman-desktop.io/docs/configuration/settings-reference)
- **Signing/sandbox posture** — Podman Desktop is an Electron app and needs Electron-specific hardened-runtime exceptions (notably JIT) that a native Swift app does not. This illustrates why entitlements should be derived from actual functionality rather than copied from a comparable. The Mac download should still be verified as Developer ID signed/notarized in release QA **(verify exact published entitlement set)**.
- **Managed configuration** — the product has three clear layers: user `settings.json`, administrator `default-settings.json`, and `locked.json`. On macOS the managed files live in `/Library/Application Support/io.podman_desktop.PodmanDesktop/` and can be delivered by Jamf, Intune, Kandji, SimpleMDM, a PKG, or automation. Defaults seed absent settings without overwriting existing choices; locked keys always read the managed value and show a lock icon in UI. Proxy, telemetry, registries, and feature availability are examples. This is one of the best documented precedence models. [Podman managed configuration](https://podman-desktop.io/docs/configuration/managed-configuration)
- **Licensing** — Podman Desktop is open source and does not add desktop-app activation. It demonstrates that local container management does not inherently need an account or license service.
- **Telemetry and privacy** — `telemetry.enabled` is documented as anonymous usage data sent to Red Hat and defaults to true; it can be changed in Settings > Preferences or disabled and locked by an administrator. The welcome flow asks about telemetry. Defaults-on is a poor fit for a personal fleet tool, but the visible control and managed override are worth copying. [Podman settings reference](https://podman-desktop.io/docs/configuration/settings-reference) · [managed telemetry](https://podman-desktop.io/docs/configuration/managed-configuration-use-cases)
- **Logs and support bundle** — Help > Troubleshooting > Logs shows application logs; Gather Logs saves a ZIP to a user-chosen location. Repair & Connections separately provides engine ping, container checks, provider reconnect, and destructive cleanup. A Stores tab reveals the frontend's last event state and permits refresh/clear. Local creation with no automatic upload is an excellent privacy boundary. [Podman Desktop logs](https://podman-desktop.io/docs/troubleshooting/access-logs)

### Rancher Desktop

- **Install/uninstall** — the Mac app is installed conventionally and removed from Applications. A factory reset (UI or `rdctl`) removes the VM and most data first; snapshots and some caches are deliberately preserved unless separately selected/deleted. Deployment profiles survive reset and uninstall. The docs clearly distinguish "remove app", "reset runtime", "keep recoverable snapshots", and "remove everything". [Rancher Desktop installation/uninstall](https://docs.rancherdesktop.io/getting-started/installation/)
- **Updates** — Preferences > Application > General allows automatic updates. Availability and release notes are shown; the update downloads and is applied with an explicit restart. This gives the user a safe interruption point instead of restarting a working runtime without warning. [Rancher Desktop update settings](https://docs.rancherdesktop.io/ui/preferences/application/general/)
- **Privilege boundary** — administrative access is an optional setting for bridged networking and the default Docker socket; without it, Rancher uses its user-owned socket/context. The app may need authorization again after reboot because `/var/run` is transient. Like Docker and OrbStack, it makes compatibility-related privilege optional. [Rancher Desktop general settings](https://docs.rancherdesktop.io/ui/preferences/application/general/)
- **Managed preferences** — deployment profiles support both first-time defaults and locked settings at user or system scope. On macOS they are explicit `.plist` files; system profiles live in `/Library/Preferences`, user profiles in the user's Preferences folder, and `rdctl create-profile` can generate them from tested JSON. Locked wins over defaults. The UI-derived generation path helps admins avoid hand-writing an invalid schema. [Rancher deployment profiles](https://docs.rancherdesktop.io/how-to-guides/generating-deployment-profiles/)
- **Telemetry and diagnostics** — anonymous statistics are a discrete preference and the docs explicitly say workload details are not collected. Diagnostics run locally at every launch, show failed-check counts and remediation, can be rerun, and are not sent to a server. Individual irrelevant checks can be muted. Troubleshooting separately exposes the log folder, debug logging, reset Kubernetes, and factory reset. [Rancher statistics](https://docs.rancherdesktop.io/ui/preferences/application/general/) · [local diagnostics](https://docs.rancherdesktop.io/ui/diagnostics/) · [troubleshooting](https://docs.rancherdesktop.io/ui/troubleshooting/)
- **Licensing** — the open-source desktop product does not require activation. Commercial account state is not allowed to become a local runtime availability dependency.

### Tailscale (remote fleet and Mac MDM analogue)

- **Install and Mac variants** — Tailscale offers a standalone package, Mac App Store app, and open-source build. The standalone variant uses a system extension while the App Store variant does not; MDM sequencing matters because installing the VPN profile before the app can leave the network extension unable to start. Its deployment guide gives exact Team ID/bundle ID payloads and distinguishes system policy from user defaults. [Tailscale Mac install](https://tailscale.com/docs/install/mac) · [Mac MDM deployment](https://tailscale.com/docs/integrations/mdm/mac)
- **MDM and managed state visibility** — configuration profiles can reduce consent prompts, install required extension/VPN approvals, enforce policy, and control standalone auto-updates. The client rereads policy on launch, can display "Managed by …", and exposes effective policy plus its origin/errors through `tailscale syspolicy list`. This makes policy precedence diagnosable instead of mysterious. [Tailscale MDM deployment](https://tailscale.com/docs/integrations/mdm/mac) · [system-policy keys](https://tailscale.com/kb/1315/mdm-keys)
- **Pairing and approval** — a new device first authenticates to a user/control-plane identity. With Device Approval enabled it remains unable to send or receive fleet traffic until an administrator reviews and approves it. Pre-approved, expiring enrollment keys support unattended servers, and approval can be revoked independently of deleting the software. [Tailscale device approval](https://tailscale.com/docs/features/access-control/device-management/device-approval)
- **Trust establishment beyond discovery** — Tailnet Lock requires a trusted fleet node to sign a new node's public key. This keeps network discovery/control-plane distribution separate from cryptographic trust and provides multiple signing nodes, signed key rotation, recovery secrets, change logs, and retroactive signing-key revocation. It is more machinery than an eight-Mac personal fleet needs, but its state model is exemplary. [Tailnet Lock](https://tailscale.com/docs/features/tailnet-lock) · [lock operations](https://tailscale.com/docs/reference/tailscale-cli/lock)
- **Identity lifecycle** — private node keys are generated locally; the public key is bound to machine and user identity. Node keys rotate and normally expire; expiry cuts connectivity, while a short temporary extension provides recovery for otherwise unreachable machines. Removing a device immediately revokes its node key fleet-wide. Enrollment/auth keys have their own shorter expiry and revoking one does not automatically revoke already-enrolled devices—an important distinction for Flotilla's pairing secrets versus identity certificates. [node keys](https://tailscale.com/docs/concepts/node-keys) · [key expiry](https://tailscale.com/docs/features/access-control/key-expiry) · [auth keys](https://tailscale.com/docs/features/access-control/auth-keys) · [device removal](https://tailscale.com/kb/1260/device-remove)
- **Authorization** — authentication of a device is not treated as blanket access. Tailscale applies policy, device tags/roles, and optional posture constraints after identity verification. Flotilla is much smaller, but should still distinguish "valid certificate", "paired peer", and "allowed operation".
- **Updates and fleet risk** — Tailscale can expose and MDM-control auto-update policy across Macs. Its warning not to force reauthentication over the only remote connection without an alternate recovery path generalizes directly to remote app/runtime upgrades: never make a change to every host at once when that same path is required to repair it. [Tailscale key expiry](https://tailscale.com/docs/features/access-control/key-expiry) · [security practices](https://tailscale.com/docs/reference/best-practices/security)

### Apple platform, Sparkle, and Jamf baseline

- **Developer ID distribution** — outside the Mac App Store, sign every executable with Developer ID, enable hardened runtime, include a secure timestamp, remove `get-task-allow`, notarize with `notarytool`/Xcode, and staple the ticket to the deliverable. Notarization scans for malware and signing problems; it is not App Review. App Sandbox is optional for Developer ID distribution and separate from hardened runtime. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) · [distribution preparation](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution)
- **Least entitlements** — hardened-runtime exception entitlements weaken protections and Apple says to use only those that are necessary. A native Swift app has no reason to inherit Electron's JIT/unsigned-executable-memory exceptions. Flotilla's external `container` CLI execution makes App Sandbox a poor default; this should be a deliberate, documented decision rather than falsely claiming that notarization implies sandboxing. [Apple hardened runtime](https://developer.apple.com/documentation/security/hardened-runtime)
- **Sparkle trust** — Sparkle signs update archives/deltas with Ed25519 and also validates Apple code signing. Its private update key is stored in Keychain; the public key is embedded in the app. It supports signed feeds, atomic replacement, delta checksum verification, and fallback to the full update when a delta cannot be safely applied. Key rotation must be staged: Sparkle permits changing the Developer ID certificate or EdDSA key in one trusted update, not both at once. [Sparkle setup/security](https://sparkle-project.org/documentation/) · [delta fallback](https://sparkle-project.org/documentation/delta-updates/) · [security history](https://sparkle-project.org/documentation/security-and-reliability/)
- **Sparkle rollout controls** — appcasts support seven-group phased rollout, channels, OS/version gating, minimum system version, and critical updates. Manual checks and critical releases bypass phased rollout. Sparkle 2 intentionally does not support downgrade installation, so rollback must be an explicit operational release/reinstall strategy rather than a hidden updater switch. [publishing an update](https://sparkle-project.org/documentation/publishing/) · [Sparkle upgrade notes](https://sparkle-project.org/documentation/upgrading/)
- **Sparkle sandbox integration** — if Flotilla ever adopts App Sandbox, Sparkle requires its Installer XPC service plus specific communication entitlement; a downloader XPC service can isolate network access. All nested helpers must be correctly re-signed and notarized. Keeping Sparkle current is itself security work; its security history includes updater/XPC vulnerabilities. [Sparkle sandboxing](https://sparkle-project.org/documentation/sandboxing/) · [security and reliability](https://sparkle-project.org/documentation/security-and-reliability/)
- **Jamf certificates and settings** — Jamf configuration profiles can deliver PKCS#12 identity payloads for a small static fleet or use SCEP for per-device enrollment/renewal. A Custom Settings payload can install managed values in the app's preference domain. Managed certificate private-key ACL/access from a Developer ID app must be proven on the actual managed Macs before the design is declared complete **(verify in Phase 6)**. [Jamf SCEP profile](https://learn.jamf.com/r/en-US/technical-articles/Creating_a_Configuration_Profile_with_a_SCEP_Payload)

## 2. Patterns worth stealing

- **Separate four deployment layers: app, Apple `container` runtime, Flotilla data/identity, and managed policy.** Podman and Rancher show why uninstalling one layer must never silently destroy the others. Flotilla should offer "Remove app", "Remove Flotilla settings/logs", "Remove fleet identity and trust", and a separately explained route to Apple's runtime uninstaller.
- **Operate unprivileged, elevate only for the signed Apple package.** Docker, OrbStack, and Rancher all make optional host integration a narrow consent event. Flotilla itself does not need an always-root helper; the settled one-click `container` bootstrap should hand the signed `.pkg` to the system installer and let macOS request authorization.
- **Use explicit effective-value precedence and show its source.** Copy Podman's defaults/locked split and Tailscale's effective-policy diagnostics: managed value > local user choice > built-in default. A managed control is visibly locked and says which profile/domain supplied it. This prevents operators debugging a UI toggle that MDM silently overrides.
- **Make discovery non-authoritative.** Tailscale's best lesson is that seeing a device is not trusting it. Bonjour supplies an endpoint and untrusted display metadata only; a separate mutually authenticated pairing/approval step supplies identity.
- **Model enrollment, identity, authorization, expiry, and revocation separately.** A pairing secret is short-lived and single-use; a certificate is a device identity; allowlist membership authorizes a peer; certificate expiry/rotation is lifecycle; revocation removes authorization immediately. Conflating these is how reusable bootstrap secrets or stale certificates become permanent back doors.
- **Give trust changes a human-verifiable ceremony.** Show both device names, roles, full fingerprint, a compact grouped fingerprint/short authentication string, and the consequences of approval. Require approval at both ends for manually generated identities. A QR code is a transport for the same authenticated fingerprint—not proof by itself.
- **Use local-first diagnostics.** Rancher and Podman run health checks and create bundles locally without automatic upload. A Flotilla support bundle should be previewable, redacted, saved to a user-selected path, and never transmitted by the app.
- **Keep recovery and destructive actions visibly distinct.** "Reconnect", "restart listener", "re-run preflight", "export diagnostics", "reset trust", and "erase all data" should not be interchangeable. Docker's crowded Troubleshoot surface shows the risk; Rancher's confirmations and preserved snapshots are better.
- **Create an update interruption point.** Rancher's download-then-restart UI is well suited to a host process serving remote actions. Finish active requests, stop accepting new ones, show "restart to update", then relaunch. Never kill a host mid-mutation.
- **Use two independent update trust checks.** Require both a valid Developer ID/notarized app and Sparkle Ed25519 archive signature. Keep release signing credentials separate from source control and stage any key/certificate rotation.
- **Canary before fleet rollout.** Sparkle's seven rollout groups are designed for public populations, not eight named Macs. For Flotilla, update the laptop/client and one noncritical host first, verify protocol/runtime health, then proceed host by host. Preserve at least one alternate administrative path to every remote Mac.
- **Design diagnostics and audit records for privacy at capture time.** Use stable random host IDs rather than usernames or hardware serials, log fingerprints only in shortened form, redact tokens/registry credentials/paths, and put request metadata—not container environment contents or streamed terminal data—in the operational audit log.

## 3. Anti-patterns / things to avoid

- **A monolithic uninstaller.** Docker's warning and Podman's multi-page cleanup demonstrate the danger of equating removal of a GUI with deletion of runtime data. Never delete containers/images, Apple `container`, identities, or MDM policy merely because Flotilla.app is trashed.
- **Silent privileged installation.** This is already rejected in `DECISIONS.md`. Do not add a privileged helper merely to suppress the Apple package authorization dialog or to make a personal deployment look "zero touch".
- **Security by notarization alone.** Notarization is malware/signature screening, hardened runtime is process hardening, and App Sandbox is resource confinement. They are different controls. A notarized but broadly entitled app, or a sandboxed app with unnecessary exceptions, is not automatically safe.
- **Copying another app's entitlements.** Electron comparables require JIT-related exceptions that native Flotilla should not have. Disable library validation, unsigned executable memory, DYLD exceptions, `get-task-allow`, Apple Events, broad file access, and Keychain sharing should all be absent unless a tested requirement proves otherwise.
- **Treating Bonjour name/IP as identity.** mDNS is spoofable and routed manual entries are typo-prone. Never auto-approve a discovered peer, pin only a hostname, or let a renamed discovery record silently replace a pinned certificate.
- **Bare TOFU hidden behind a Connect button.** A first connection that records whichever certificate answered is vulnerable to an active attacker. Pairing must require out-of-band fingerprint comparison/scan or managed trust, and should say when the presented identity differs from the saved one.
- **One shared certificate or reusable pairing key for the fleet.** Compromise of one Mac would impersonate every host. Generate/deliver a unique identity per device; use one-time, expiring bootstrap material; never embed a `.p12` passphrase or private key in app defaults, logs, or source.
- **Static pins with no rotation plan.** Raw leaf fingerprint pinning is simple for Phase 2 but certificate renewal changes the fingerprint. Provide overlap (old and new identity), authenticated rotation approval, clear expiry warning, and an emergency manual re-pair path before certificates begin expiring.
- **Revocation that only updates the UI.** Removing a peer must delete/deny its authorization, close existing connections, reject session resumption/new requests, and be auditable. Uninstalling a remote app is not fleet revocation—Tailscale makes this distinction explicit.
- **mTLS equals authorization.** A cryptographically valid peer must still be on the correct allowlist and role. The host must expose typed, bounded `container` operations—not a generic remote shell—and reject unknown wire versions, oversized frames, invalid arguments, and requests inappropriate for the peer's role.
- **Centralized trust without recovery keys or quorum thinking.** Tailscale's Tailnet Lock shows both the strength and operational cost. For this personal eight-node fleet, do not build a distributed CA/control plane; do keep more than one trusted way to re-enroll a host and document recovery if the laptop identity is lost.
- **Auto-update every host at once.** A bad binary, protocol break, expired signing credential, or changed entitlement could remove the only management path. Do not make "Update all" the initial behavior, and never rely on the path being upgraded as the only rollback channel.
- **Calling Sparkle a rollback system.** Sparkle 2 rejects downgrade semantics. Retaining an older notarized artifact and appcast is useful, but restoration is an explicit reinstall/release operation with data-schema compatibility checks.
- **Updating a managed mini through both Sparkle and Jamf.** Two authorities create races and compliance drift. A managed preference must disable Sparkle application checks/installation on Jamf-managed Macs; Jamf owns those versions, exactly as settled in `DECISIONS.md`.
- **Telemetry bundled into support consent.** "Send usage statistics" must not be a condition of diagnostics, updates, or crash recovery. Do not copy Docker/Podman's default-on analytics. Do not upload a support ZIP merely because it was generated.
- **Crash reports containing workload data.** Container names, image references, commands, environment variables, mount paths, logs, IPs, hostnames, and terminal transcripts can be sensitive. Capture the minimum, redact before persistence, and make any future remote crash service opt-in.
- **Logs as an unbounded second database.** Rotate by size/age, use privacy-marked Unified Logging fields, avoid duplicate command output, and provide a "reveal logs" and "export redacted bundle" path. Debug logging should be time-limited and visibly enabled.
- **License/account gating for a personal utility.** Docker and OrbStack need commercial entitlement systems; Flotilla does not. Activation, cloud accounts, mandatory analytics endpoints, SSO, and seat enforcement would add failure modes and privacy cost without serving the stated goal.

## 4. → Proposed for Flotilla

1. **[core] Phase 1 — Ship as an unprivileged Developer ID app with a conventional drag-to-Applications install.** Detect whether the app is running from a translocated/read-only location and guide the user to Applications. Keep the already-settled runtime bootstrap separate: download Apple's signed `.pkg`, verify the release/checksum/signature information available from Apple, then invoke the system installer with visible user authorization. **Confirms `DECISIONS.md`; no conflict.**
2. **[core] Phase 1 — Define uninstall/data semantics before creating persistent state.** Document app removal separately from (a) local preferences/history/logs, (b) Keychain identity and peer trust, and (c) Apple `container` and its containers/images. In-app "Reset Flotilla" must offer export, enumerate what will be deleted, require confirmation, and never remove the Apple runtime by default. Host mode should be stopped cleanly before identity deletion. **Extends `PLAN.md` Phase 1 operations.**
3. **[core] Phase 1, release gate used again in Phase 5 — Adopt the Mac security baseline now.** Enable hardened runtime; sign every nested executable/framework with Developer ID and secure timestamps; remove `get-task-allow`; keep library validation on; notarize and staple; verify with `codesign`, `spctl`, and a clean-Mac launch test. Maintain an explicit entitlement inventory in release notes/checks. **Extends the Phase 5 signing line by moving build hygiene earlier; distribution notarization still lands in Phase 5.**
4. **[core] Phase 1 — Do not enable App Sandbox for v1.** Flotilla must discover and execute an externally installed `container` CLI and later accept/listen for fleet connections; a useful sandbox configuration is likely to require brittle exceptions and may block the chosen CLI integration. Use hardened runtime, least privilege, strict CLI argument construction, and Keychain instead. Re-evaluate only after a spike proves the full CLI/update/Bonjour path. **Explicit extension/clarification of `DECISIONS.md`, not a transport change.**
5. **[core] Phase 1 — Minimal entitlements and privacy declarations only.** No JIT, unsigned executable memory, disabled library validation, DYLD, Apple Events, contacts/location, broad Keychain group, or debug entitlement. Add local-network usage text and declared Bonjour service before Phase 2. If sandboxing is later adopted, add only network client/server and Sparkle's documented XPC integration. **Extends `PLAN.md`; no conflict.**
6. **[core] Phase 1 — Structured local operations logging.** Use macOS Unified Logging with categories for app lifecycle, CLI preflight/execution, transport, pairing/trust, update, and managed policy. Default to metadata and durations; never record container environment variables, registry credentials, private keys, pairing tokens, full terminal input/output, or full cert material. Mark dynamic values private, rotate any file logs, and make debug mode time-limited. **Extends Phase 1 and supports all later phases.**
7. **[core] Phase 1 — Local diagnostic checks and a user-saved redacted support bundle.** Include app/build/macOS/Apple `container` versions, architecture, CLI path/preflight, recent redacted Flotilla logs, effective nonsecret settings and their sources, listener/browser status, protocol compatibility, certificate expiry/short fingerprints, and failed health checks. Show a manifest and estimated sensitivity before saving. No automatic upload and no server-side diagnostic ID. **Extends `PLAN.md`; modelled on Rancher/Podman.**
8. **[core] Phase 1 — No license, activation, mandatory account, analytics, or remote crash SDK.** Flotilla is personal/non-commercial and should work entirely offline except for explicit runtime/app update checks and fleet connections. Provide an About/Privacy view listing network destinations and stored data. Rely on local Apple crash reports initially. **Confirms product context; deliberately skips comparable commercial machinery.**
9. **[core] Phase 2 — Keep TLS 1.3 mTLS and unique per-device Keychain identities exactly as decided.** Generate a non-exportable private key where practical; store identity/trust records with restrictive Keychain accessibility appropriate to host mode; never fall back to plaintext or server-only TLS. Separate identity certificate validation from local fingerprint allowlist authorization. Test locked-screen/reboot behavior on a real host. **Confirms `DECISIONS.md` and `reference/networking-mtls-bonjour.md`.**
10. **[core] Phase 2 — Make Bonjour/manual endpoints untrusted until pairing succeeds.** Discovery may populate name/address/port only. Manual and Bonjour paths must enter the same trust flow. Display a warning on identity change; never silently replace a saved pin because the hostname or IP matches. Bind/advertise only while host mode is enabled, use a configurable high port, and fail closed on every TLS verification path. **Confirms the mandatory manual-add decision and extends its threat model.**
11. **[core] Phase 2 — Add a real two-sided pairing ceremony around the settled fingerprint exchange.** Show device role, full SHA-256 certificate fingerprint plus a grouped human-checkable form/QR, require explicit approval on both peers, and persist who/when/how it was approved. QR/paste imports a fingerprint; it does not bypass confirmation. Pairing attempts expire, are rate-limited, and reveal no private key. A peer stays `discovered`/`pending` until both allowlists agree. **Extends—but does not replace—the manual cert-pinning flow in `PLAN.md`.**
12. **[core] Phase 2 — Enforce application authorization after mTLS.** Host mode accepts only pinned client identities and a fixed typed RPC allowlist. Validate wire protocol version, operation, argument schema, message length, concurrency, deadline, and cancellation before starting `container`; return bounded errors. Do not expose an arbitrary command string or shell in Phases 2–3. Record request ID, peer ID, operation, result, and duration without payload secrets. **Extends the Phase 2 wire security model; consistent with the rejected SSH/gRPC alternatives.**
13. **[core] Phase 2 — Implement immediate local revocation.** Removing a peer must update the allowlist atomically, close its active connections, reject new handshakes/requests, clear resumable pairing state, and leave a nonsecret audit entry. Removing a discovered endpoint is not the same action as revoking its identity. Provide "block" versus "forget address" language. **Extends `PLAN.md` host onboarding/trust.**
14. **[core] Phase 2 — Add certificate lifecycle fields from day one.** Persist issuer/source (`self-generated`, `manual`, `managed`), serial/fingerprint, creation, expiry, and last-seen identity. Warn well before expiry. Design for overlapping old/new pins and authenticated rotation, but keep manual re-pair as the v1 recovery path. Never auto-accept a changed leaf certificate solely because the old one is near expiry. **Extends the static fingerprint recipe to avoid a future lockout.**
15. **[core] Phase 2 — Protocol/version handshake and safe mixed-version behavior.** Exchange app version, wire min/max, capabilities, runtime version, and host mode before accepting mutations. Compatible older peers get reduced capabilities; incompatible peers remain visible with an actionable update message. Unknown operations fail closed. This is required before Phase 5 can safely stagger app updates. **Extends `PLAN.md` Phases 2 and 5.**
16. **[core] Phase 3 — A trust-management view, not just a host list.** Per peer show connection state separately from trust state, role, identity source, short fingerprint, certificate expiry, last successful authentication, last address, app/runtime version, and managed status. Actions: compare fingerprint, approve pending, revoke, rotate/re-pair, export public identity, and view audit events. Never display `healthy` merely because Bonjour is present. **Directly maps to Phase 3 host onboarding/trust management.**
17. **[later] Phase 3 or 4 — Fine-grained roles if the fleet grows beyond one client.** Start with `client-controller` and `host` certificate roles; later consider read-only observers versus operators. Avoid a general ACL language for eight personal Macs. **Extends `PLAN.md`; defer until there is a second real controller/user.**
18. **[core] Phase 4 — Treat interactive exec as a new security boundary.** Require a fresh visible user action, display target host/container, limit session lifetime and concurrency, never log keystrokes/transcript by default, terminate on revocation/disconnect, and make host-side session presence visible. Do not let the Phase 2 generic request API accidentally enable exec early. **Extends Phase 4; consistent with typed transport.**
19. **[core] Phase 5 — Integrate current Sparkle 2 with dual trust.** HTTPS appcast on GitHub releases; `SUPublicEDKey`; Ed25519-sign every full/delta artifact; require valid Developer ID signatures; optionally require a signed feed; retain signing keys in a dedicated protected Keychain/secret store outside the repository. Pin Sparkle to a reviewed current release and treat Sparkle security updates as release blockers. **Confirms the settled Sparkle choice and `reference/sparkle-updates.md`.**
20. **[core] Phase 5 — Separate check, download, and install/restart controls.** Default to periodic check and notification; allow background download; require an explicit restart point while the app is serving host mode. "Check for Updates…" remains available. Before restart, stop new remote mutations, let bounded active requests finish or cancel safely, persist no partial trust change, then relaunch and run preflight. **Extends Phase 5 with host-safe behavior.**
21. **[core] Phase 5 — Release gates and atomic failure handling.** CI/release procedure must archive, sign, notarize, staple, verify, run clean-install and N-1 upgrade tests, test a failed delta falling back to full, validate appcast URLs/signatures/version monotonicity, and smoke-test both client and host modes. Do not publish the appcast until the immutable release asset and notarization are verified. **Extends `reference/sparkle-updates.md`.**
22. **[core] Phase 5 — Canary and rollback runbook.** Keep the previous notarized full artifact and compatible data schema; upgrade the controller and one noncritical host, verify reconnect/runtime actions, then upgrade hosts one by one. A bad release is withdrawn/superseded in the appcast; recovery uses an explicit reinstall of the previous notarized app only if its data schema is compatible. Do not advertise one-click downgrade—Sparkle 2 does not provide it. Preserve local/physical access or Jamf as an alternate recovery channel. **Extends Phase 5; no conflict.**
23. **[later] Phase 5 — Sparkle phased rollout/channels and deltas.** Use a stable/beta channel only after multiple release tracks are genuinely useful. Public seven-group phased rollout is low-value for eight named Macs; a manual named-host canary is clearer. Add deltas only after full-update reliability is proven, since the app is Apple-Silicon-only and likely modest in size. **Defers optional features already mentioned in the Sparkle reference.**
24. **[core] Phase 6 — One managed authority with explicit precedence.** Managed preference/profile > local preference > built-in default. Required managed keys: mode, listen port/interface policy, app-update authority, identity lookup selector, trust-anchor/pin set, allowed client identities/roles, Bonjour advertise policy, diagnostic/debug policy, and optionally minimum accepted client version. Managed UI controls are locked and show "Managed"; a diagnostics page shows effective value, source, validation errors, and last reload. **Extends `reference/jamf-config-profile.md` using Podman/Tailscale's best patterns.**
25. **[core] Phase 6 — Unique MDM-delivered identity per Mac.** For the small initial fleet, a separate passphrase-protected PKCS#12 payload per device is acceptable; do not scope one shared `.p12` to a group. Prefer SCEP/ACME when renewal/revocation infrastructure is available. Select identities by certificate attributes/managed identifier, not a freely editable file path, and verify private-key access after reboot and with no user session assumptions. **Refines the reference note; does not change mTLS.**
26. **[core] Phase 6 — Prove the Jamf profile on a staged smart group.** Test app install before profile, profile before app, replacement/renewal overlap, removal, reboot, locked screen, user logout, network segmentation/manual host entry, and a revoked controller. Validate that managed settings cannot be overridden and that profile removal produces a safe `managed identity unavailable` state rather than generating an unapproved replacement identity. **Extends the Phase 6 verification plan.**
27. **[core] Phase 6 — Jamf owns application updates on managed minis.** A managed setting disables Sparkle application checks/download/install and identifies Jamf as the update source; unmanaged Macs continue using Sparkle. Roll out via a canary smart group, require post-install app/transport/runtime health inventory, then expand scope. Keep the prior Jamf package for explicit recovery. **Confirms `DECISIONS.md`.**
28. **[later] Phase 6 — Managed trust rotation and revocation distribution.** Deliver overlapping old/new trust anchors or fingerprints, activate the new set, verify all peers, then remove old trust. Use profile version/generation numbers and reject rollback to older policy. For urgent revocation, MDM updates the deny/allow state and Flotilla closes matching live connections when preferences change or on next managed refresh. **Extends static managed allowlists.**
29. **[later] Phase 6 — Optional crash reporting only if local reports prove insufficient.** If added, use a clearly named opt-in separate from usage analytics, document the processor/retention/endpoints, scrub host/container/network/path data before submission, permit preview where practical, and let MDM force it off. No session replay. **Deliberately later for privacy and because the app is personal.**
30. **[skip] All phases — Commercial licensing/activation, cloud account, SSO, seat reporting, and an online fleet control plane.** Docker/OrbStack need these for a business; Flotilla does not. They would add availability, privacy, and key-management risks and conflict with the personal/local-first goal.
31. **[skip] All phases — A custom root daemon or silent privileged updater.** The one-app/two-mode architecture, Developer ID distribution, Sparkle, and Apple's authorized package installer cover the requirement. A privileged service would materially enlarge the attack surface and conflicts with the explicit rejection of silent privileged runtime installation.
32. **[skip] v1 — Distributed trust authority, shared CA service, or Tailscale-style Tailnet Lock clone.** Mutual leaf pinning plus explicit bilateral approval is proportionate for eight Macs. Revisit a real CA/control plane only if multiple administrators, unattended large-scale enrollment, or internet-wide fleet management becomes a requirement.
33. **[skip] v1 — Automatic fleet-wide update and automatic downgrade.** Use named-host canaries and one-at-a-time rollout. Sparkle is an authenticated atomic updater, not an orchestration or rollback engine; Jamf is the authority for managed hosts.
