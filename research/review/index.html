01

What the research concluded

From research/FEATURES.md §1 — the consolidated verdict of all four passes.

The research converges on a clear product: a table-first fleet console with a shallow menu-bar popover, wrapping a CLI that is far smaller than Docker's — which is good news, because it deletes half the feature list before we start (no compose, no events, no pause, no VM-sizing pane).

The differentiator no comparable has is the cross-host container list: Docker Desktop has no multi-host GUI at all, and Portainer drills into one environment at a time. The differentiator that costs the most is polling discipline, since container has no event stream — everything the UI knows, it learned by asking, so adaptive polling is a feature rather than an optimisation.

Two structural findings shape the plan. Phase 1 is bigger than PLAN.md implies — preflight, the security baseline and the settings registry all want to land there, because each is cheap now and a rewrite later. And Phases 2–4 hinge on one protocol decision made now: whether the wire carries CLI arguments or typed bounded operations (Q1).

The shape of the thing
  1. Table first, card grid demoted to a toggle — cards stop scaling around twenty rows.
  2. Popover is a glance, the main window is the product. No text entry, no destructive confirmations in the popover.
  3. Everything is polling. No docker events analogue exists.
  4. Args over the wire would make Phase 1 parity free in Phase 2 — if we accept the security posture. See Q1.
  5. Zero telemetry, zero account, stated in the UI as a feature.
The decisions only you can make
  1. Wire shape — CLI-args passthrough vs. typed bounded operations. Q1
  2. Table vs. the card grid as the default view. Q2
  3. Does host mode become stateful? Q3
  4. Two-tier managed settings + typed registry, now or never. Q4
  5. Phase 1 scope — approve §3 as-is, or trim it. Q5

04

Open questions

Nine items the research deliberately did not resolve, because each is a genuine either/or with real consequences. One is already closed. Q1 is the one that prices everything downstream.

Q1 Highest consequence · decide first

Wire shape: CLI-args passthrough, or typed bounded operations?

Two researchers reached opposite conclusions from the same facts. This one decision sets Phase 2's cost, whether Phase-1 parity is free, and how exec is gated in Phase 4 — and once a fleet is deployed, changing it is a protocol break.

RUN says Args over the wire is an "unusually strong property": every Phase-1 feature becomes a fleet feature in Phase 2 at zero marginal cost, and the command string doubles as the audit log. The host stays the stateless executor PLAN.md describes.
OPS says The host must expose typed, bounded container operations — not a generic remote shell: validate operation, argument schema, frame length, concurrency and deadline before spawning anything. Explicitly: "do not expose an arbitrary command string in Phases 2–3."

A middle path exists — args passthrough constrained by an args[0] subcommand allowlist plus per-subcommand schema validation, which keeps most of RUN's leverage while closing OPS's "remote shell" objection. It buys the property at the cost of a validation table that has to be maintained as the CLI grows. Either way it needs your call, not ours.

Q2

Table or the card grid as the default view?

UXA table — running-first, sortable, multi-select. Cards stop scaling around twenty rows; demote them to a toggle.
Existingdesign/dashboard-mockup.html is a card grid with sparklines, and it's your design.

The mockups in §2 already assume the table. Needs sign-off either way — this is the most visible reversal in the whole proposal.

Q3

Does host mode become stateful?

Two features push it there: the restart/health loop (RUN: it must run on the host peer, or closing the laptop stops restarting containers on the minis) and per-host settings get/set. Both mean host mode needs a persisted policy store.

That's a real expansion of PLAN.md's "host mode is the same binary running headless-ish", which today just executes CLI args. Accept the expansion, or accept that restart policies only apply while the client is connected — and say so in the UI, because the alternative is a policy that silently lies.

Q4

Confirm the two-tier defaults/locked managed model now?

Todayreference/jamf-config-profile.md: "if a managed value is present, it wins."
SETUpgrade to defaults-seed + locked-override before Phase 2 writes the settings accessors.

Retrofitting precedence means rewriting every accessor. Cheap now, expensive later — but it is a real scope addition to Phase 1.

Q5

Is §3's Phase 1 the Phase 1 you want?

As consolidated, Phase 1 includes volumes, networks, the settings registry, the security baseline, diagnostics and the support bundle — more than PLAN.md's Phase 1 line ("container grid, images list, run/stop/restart/remove, logs view").

Approve as-is, or cut to the PLAN.md line and push the rest to a Phase 1.5. If it gets tight, the ⌘K palette is the designated first cut.

Q6

Notifications in Phase 1 or Phase 3?

SETPer-category toggles are core in Phase 1.
UXDesign the categories in Phase 2, ship them in Phase 3.

PLAN.md doesn't mention notifications at all, so there's no prior to fall back on. Five categories are proposed; error ones are not disableable.

Q7

Should Flotilla ever write config.toml?

Reading ~/.config/container/config.toml is unambiguously good. Writing means owning a file another tool owns, on a machine you may not be sitting at, with a service restart to apply the change.

SET's recommendation: read in Phase 1, edit locally in Phase 3, edit remotely only if it proves necessary.

Q9

Record "no App Sandbox for v1" as a decision?

OPS makes the case: we execute an external CLI and listen for network connections, so a useful sandbox needs brittle exceptions. DECISIONS.md is currently silent on sandboxing.

Worth recording explicitly so it isn't re-litigated — including that notarization ≠ sandboxing ≠ hardened runtime. We still do Developer ID + hardened runtime + least entitlements.

Deliberately not doing

The most useful output of the research: a scope that is smaller than Docker Desktop's on purpose, for three separate reasons.

Because the runtime can't back it container 1.1.0 has no such command — drawing the button would be a lie

  • pause / resume, rename, live resource update, top, commit, diff — no backing commands.
  • Compose as an execution engine (stacks, up/down, dependency ordering). Compose-file import into a pre-filled run sheet is the honest version.
  • Event-driven UI — no docker events analogue. Everything is polling; that's why polling discipline is a Phase 3 core feature.
  • CPU/RAM/disk resource sliders — there is no shared host VM to size. One micro-VM per container; faking the pane invents a control that does nothing.
  • File-sharing / bind-mount pane — no VirtioFS-vs-FUSE choice exists; mounts are per-run, so they belong in the run sheet.
  • Finder-mounted container filesystems — needs a FileProvider/FUSE-class extension and makes no sense for a remote Mac.

Because it's the wrong product personal, non-commercial, local-first

  • Accounts, sign-in, licensing, activation, SSO, cloud control plane — Docker's reappearing "You can do more when you sign in" banner is the single most-complained-about thing in the entire survey.
  • Telemetry / analytics of any kind — the correct amount for a personal app is zero, and saying so in Settings is itself a feature. (Docker and Podman both default it on.)
  • Image vulnerability scanning — needs a bundled scanner + vuln DB + updates. Enormous, and orthogonal to a fleet manager.
  • Extensions / marketplace, Dev Environments, Learning Center, embedded AI assistant, in-app notification centre — product-growth surfaces, not features.
  • Docker Hub browse in-app — a "pull by ref" field covers the real need.
  • Kubernetes or any orchestrator view; multi-host stack deployment — the fan-out primitives give most of the value without an orchestrator.
  • Customizable nav tabs, in-app theme/accent picker, a web dashboard (would mean an HTTP server on every host, contradicting mTLS-only), a "mini player" window (our popover already is that).

Because it's disproportionate machinery for eight personal Macs with one administrator

  • Distributed trust authority / shared CA / Tailnet-Lock clone — mutual leaf pinning plus explicit bilateral approval is proportionate. Revisit only with multiple administrators.
  • A custom root daemon or privileged updater — Developer ID + Sparkle + Apple's authorized installer cover it; a privileged helper would materially enlarge the attack surface.
  • Automatic fleet-wide update, and automatic downgrade — a bad binary could remove the only management path. Named-host canaries, one at a time.
  • A general ACL language / fine-grained roles — start with client-controller and host.
  • Shell-completion install / PATH management — the container pkg owns /usr/local/bin.
  • Beta/experimental features tab — noise inside a pre-1.0 app.
  • container machine management — read-only machine list in host detail is the ceiling. USB passthrough, sound — irrelevant to headless fleet Macs.
