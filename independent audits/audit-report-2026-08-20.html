Summary Findings Security UI Gaps Redundancy Roadmap
Independent source audit · 20 August 2026

Flotilla is capable—but not yet fleet-ready.

The local macOS product is far more complete than its README suggests. Its strongest asset is a well-tested, default-deny command boundary. Its largest risks sit one layer lower: process execution can hang indefinitely, destructive behavior changes by entry point, and visible settings promise capabilities that do not exist yet.

01 · Executive readout

Strong core, uneven product contract

The code shows repeated evidence-driven hardening. The remaining problems are not generic “add validation” advice; they are concentrated mismatches between validated intent, execution mechanics, and what the interface tells the user.

Verdict: safe for continued local development; not ready for remote-host or public distribution.

The local-only app has a credible security spine: arguments are structured, host paths are policy-gated, remote-only exposures are explicitly catalogued, support bundles are audited after redaction, and non-zero CLI exits surface. Before Phase 2, however, the process runner needs real resource control and the unresolved remote publishing/plugin policies must close. Before anyone depends on the UI for data safety, all deletion paths must share one confirmation policy.

!Immediate focus: make the execution boundary enforce time, output, and cancellation; route every destructive action through one gateway; redact audit records before Phase 2 adds logging.

02 · Detailed findings

Fourteen actionable findings

Use the filters to isolate security, UI, operational, or maintainability work. Expand each item for impact, evidence, and a concrete remediation.

F-01Timeout metadata is calculated, then discarded before executionHigh Security · Availability · Phase 2 blocker

Impact

A hung container subprocess can occupy a detached task forever. Cancelling a polling task does not terminate the child. In Phase 2, a remote caller could consume process slots indefinitely even though every command already carries a timeout hint.

Recommendation

Change the host contract to accept ValidatedCommand or an execution policy object. Enforce a monotonic deadline in the process runner, terminate then kill on expiry, cap concurrent children, and make task cancellation close pipes and end the process.

Allowlist.swift:278–280, 323–337ContainerCLI.swift:183–198ContainerHost.swift:48–70
F-02Sequential pipe draining can deadlock and output is unbounded in memoryHigh Reliability · Availability

Impact

The runner blocks while reading stdout to EOF before it reads stderr. A child that fills the stderr pipe while stdout remains open can block permanently. Both streams are also accumulated without a byte ceiling, so a noisy command can spike memory.

Recommendation

Drain stdout and stderr concurrently with readability handlers or async bytes; enforce per-stream and combined byte limits; preserve a truncated marker in CommandResult; add an adversarial test process that fills both pipes.

ContainerHost.swift:56–69 The current order is run → read stdout to EOF → read stderr to EOF → wait.
F-03Container deletion bypasses confirmation from the context menuHigh UI consistency · Data loss

Impact

The row trash button opens a named confirmation, but right-click → Delete calls model.perform(.delete) immediately. Containers and Machines also ignore the “Confirm destructive actions” preference, while images, volumes, and networks honor it. The same action has different safety depending on resource and entry point.

Recommendation

Create one requestDelete(resource:source:) path that reads policy, names the target, and owns confirmation. Route rows, cards, menus, keyboard shortcuts, detail headers, and bulk actions through it. Add tests for every entry point and for both preference states.

ContainersView.swift:433–434, 490–504, 565–592MachinesView.swift:140–155SettingsView.swift:281–285
F-04Future audit records expose environment values and build argumentsMedium Security · Privacy · Phase 2

Impact

auditDescription joins canonical arguments verbatim. Valid commands may contain --env DATABASE_PASSWORD=… or --build-arg TOKEN=…. The code explicitly describes this string as what a host peer logs, turning normal container secrets into log data.

Recommendation

Model audit fields structurally. Keep command path, mutation class and non-sensitive operands, but render sensitive flag values as KEY=<redacted>. Make raw argv unavailable to the audit logger by type, not convention.

Allowlist.swift:323–337, 610–625, 672–676
F-05Host-path authorization retains a symlink check/use raceMedium Security · Known residual

Impact

An allowed path is resolved and checked, but the original string is later passed to another process. A writable object can be repointed after validation, allowing a bind, copy or build context to resolve outside its permitted root. The code and prior review acknowledge this TOCTOU gap.

Recommendation

For Phase 2, avoid treating a preflight string check as complete authorization. Narrow writable roots, require existing inputs, prefer resolved canonical paths, and design the host executor around stable file descriptors or a privileged helper that validates at use time where the CLI surface allows it.

MountPolicy.swift:68–73, 93–119Prior security review:74–108, 211–219
F-06Two remote-execution policy namespaces remain unresolvedMedium Security · Phase 2 blocker

Impact

A future peer can request run --publish 0.0.0.0:…, exposing a service on every host interface. Volume driver options and network plugin options are opaque forwarded namespaces; grammar validation cannot decide which keys are safe. Neither is exploitable today because the transport is absent.

Recommendation

Add host-owned publish policy (interfaces, port ranges and conflicts). Replace opaque remote plugin options with reviewed typed keys; make unknown keys local-only. Keep the entire plugin namespace closed until empirical probes or source review establish behavior.

F-07Settings visibly offer controls that do not drive any runtimeMedium UI trust · Configuration

Impact

The Binary path field is ignored because AppModel constructs LocalHost() with preflight lookup. Host mode, listen port, Bonjour and identity labels are editable before any transport exists. Sparkle toggles and channels are editable even though About correctly says update checks are not built. This makes successful saving look like successful configuration.

Recommendation

Wire Binary path into a validated resolver immediately. Mark future panes “Not available in this build” and disable inputs, or hide them outside a developer feature flag. Updates should show one honest status panel until Sparkle is installed. Add a registry test that every user-editable setting has a production consumer.

F-08The app bundle has identity but no distribution integrityMedium Release security · Operations

Impact

The packaged app is ad-hoc signed, has no TeamIdentifier, and does not enable a hardened runtime or notarization. That is appropriate for development but cannot establish publisher identity or survive a public release security review. There is also no verified update chain.

Recommendation

Create the Xcode project/release target; enable hardened runtime with a minimal entitlement inventory; Developer ID sign every nested item; notarize and staple; verify via codesign, spctl, and a clean-Mac launch. Add Sparkle only with dual signature verification and a rollback runbook.

make-app.sh:14–19, 149–157 Current bundle inspection: flags=adhoc · TeamIdentifier=not set.
F-09The 307-test suite does not exercise the SwiftUI product surfaceMedium Quality · Accessibility · Regression risk

Impact

The test target covers FlotillaCore only. The project’s own history records UI defects that compiled and passed tests: missing symbols, invisible controls, inert settings, clipped rows, stale processes and appearance drift. There is no UI test, accessibility audit, keyboard traversal test or screenshot baseline.

Recommendation

Add an Xcode UI-test target with deterministic model fixtures. Cover first run, every sidebar section, light/dark/Auto, list/cards, delete entry points, keyboard navigation, VoiceOver labels, narrow minimum window size and menu-bar/Dock modes. Keep pixel baselines to a few stable shells rather than every data cell.

Package.swift:38–47Tests/FlotillaCoreTests/ 12 test source files; no app test target.
F-10No-tag builds generate an invalid marketing-version shapeMedium Packaging · Updates

Impact

CFBundleShortVersionString is derived from git describe. With no version tag, the current bundle contains d8ba884, not a dotted numeric marketing version. This can disrupt packaging validation, version ordering and future Sparkle comparisons.

Recommendation

Require a SemVer tag for release builds, use 0.0.0 for untagged development marketing versions, and put commit identity in CFBundleVersion or a custom build metadata key. Fail the release script if either value violates its declared format.

make-app.sh:70–74, 124–132 Current plist: CFBundleShortVersionString = d8ba884.
F-11“Menu bar / Dock / Both” presents three choices but only two behaviorsLow UI consistency · Known limitation

Impact

Dock and Both both map to .regular while the MenuBarExtra always exists; “Dock only” is not dock-only. Menu-bar-only still opens a main window at launch. The UI gives these modes equal, definitive labels despite admitted behavioral collapse.

Recommendation

Until the scene can be truly hidden, offer “Dock + menu bar” and “Menu bar” only, with a note that the window opens at launch. Restore three choices only when each can be tested as a distinct state.

F-14Brand accent compilation is best-effort, so packaged UI can silently revert to blueLow Branding · Build reproducibility

Impact

If actool fails, packaging continues without NSAccentColorName. SwiftUI tint remains watermelon, while AppKit sidebar selection and focus rings fall back to the system accent. The result is exactly the mixed-palette inconsistency the centralized theme is intended to prevent.

Recommendation

Fail release builds when the asset catalog cannot compile; retain the warning-only fallback for debug builds. Verify the built asset and plist key as a packaging test.

05 · Product gaps

What is genuinely missing

These are capabilities absent from the current code, not defects in what already works. Their order reflects dependency and security cost, not feature attractiveness.

G-01 · Defining gap

Remote fleet transport and host runtime

No Network.framework transport, mTLS enrollment, Bonjour discovery, manual host store, remote host implementation, host-side state, revocation flow or wire framing exists. The cross-host table is currently “This Mac” only.

Phase 2 · large · security-critical
G-02 · Release gate

Signed, notarized, updating distribution

No Xcode archive pipeline, Developer ID identity, hardened runtime, notarization/stapling, Sparkle integration, appcast verification, canary or rollback mechanism.

Before public distribution · large
G-03 · Continuity

Persistent activity and metrics history

Events and stats are bounded in memory and reset when the app exits. Longer dashboard ranges and audit history need a store, retention policy, downsampling and truthful “since” labeling.

After execution hardening · medium
G-04 · Registry workflow

Private registry authentication

Pull and build exist, but login/logout and credential lifecycle do not. Passwords must avoid argv, live in Keychain, and reach the CLI through a reviewed input mechanism.

Security design first · medium
G-05 · Operability

Live streaming and durable cancellation

Follow mode is repeated bounded fetch, not streaming. A streaming API depends on the same process ownership, backpressure, cancellation and output budgeting required by F-01/F-02.

Build on new runner · medium
G-06 · Reach

Localization and keyboard-first navigation

Hundreds of user-facing strings are embedded in Swift, and there is no command palette. Both are low security risk but broad surface-area changes, best done after the UI contract settles.

Post-UI stabilization · medium

07 · Remediation sequence

A practical three-wave plan

This sequence keeps feature work from being built on a process boundary that will have to change underneath it.

Wave 0 · now

Make local execution bounded and safe

  1. Replace LocalHost.run([String]) with a typed execution envelope.
  2. Concurrent pipe drains, output caps, deadline, cancellation and child cleanup.
  3. Unify every delete entry point and honor both confirmation settings.
  4. Redact structured audit records.
Estimated shape: 4–7 focused engineering days + adversarial tests
Wave 1 · next

Restore an honest product contract

  1. Wire or disable inert settings.
  2. Reduce presentation choices to states that really exist.
  3. Add deterministic SwiftUI/UI tests and accessibility checks.
  4. Fix bundle version semantics and make brand assets mandatory for release builds.
  5. Refresh README and broken internal links.
Estimated shape: 5–9 days, mostly independent workstreams
Wave 2 · gate Phase 2

Open the fleet boundary deliberately

  1. Close publish-interface and plugin-option policies.
  2. Design mTLS enrollment, revocation, identity storage and persisted host policy.
  3. Enforce request concurrency, frame limits, deadlines and audit privacy on the host.
  4. Revisit path authorization’s TOCTOU limits.
  5. Only then add discovery and RemoteHost.
Estimated shape: multi-week milestone; independent security review required
08 · Audit evidence

Scope and limitations

The report is evidence-backed but not a substitute for a live hostile-environment test or a clean-Mac distribution review.

Inspected and verified

  • All Swift production and test files, package manifests and resolved architecture.

  • SwiftUI navigation, tables/cards, destructive actions, settings, menu-bar behavior and branding primitives.
  • Packaging script, built app plist and code-signature metadata.
  • Current and historical product/security decisions and prior allowlist review.

Not performed

  • No live destructive container operations or remote network penetration test.
  • No VoiceOver session or human usability study.
  • No notarization, Gatekeeper or clean-Mac installation test (the app is not distribution signed).
  • No third-party dependency CVE scan against online advisories.
  • No claim that low-priority future features are required for a local MVP.
